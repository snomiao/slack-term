slack-term

Slack for people and the agents working with them. Read, search and reply from a shell, and see exactly what will be sent before it goes.

npm install -g slack-term

Also with bun or pnpm. A smaller native Rust build covers the core commands.

Why this exists

slack-term began in March 2026 as a small tool for reading mentions and searching a workspace without opening the Slack app. Reading was the easy part. The project changed once the thing typing the commands was often an AI coding agent.

An agent that can only read is a curiosity. An agent that can write into the channel where your colleagues work is either infrastructure or a hazard. A Slack message is public, it can't really be taken back once people have seen it, and it carries your name. So most of the work here isn't the API wrapper. It's everything built around the moment of writing, and around getting a human's answer back to the agent that asked.

It is the part of the agent-yes fleet that talks to people, though neither depends on the other, and it works just as well for a person at a shell.

A confirm code that goes stale

Every gated write runs twice. The first run shows who you are, where it goes, what the conversation currently says and what you're about to add. The second run has to present a four-character code. There's no server, session or stored state behind it, because the code is recomputed from the things that must not have changed:

code = sha256(channel, thread, last message, your text, you)[:4]

The last message is the idea we like most. If someone posts between your preview and your confirm, the code no longer matches, and you see the conversation again before you can go ahead. Freshness comes from the very thing that would change your mind, not from a timer.

$ slack send "#eng" "Deploying v2 now"
  From: @alice (U00000001) — Acme
  To:   #eng
  ...recent messages...
Rerun with --code=3f9c

          bob, in #eng: "wait, hold the deploy"

$ slack send "#eng" "Deploying v2 now" --code=3f9c
Code mismatch
  ...now you see bob's message...

Switch accounts between the two runs and the code dies too. An edit or delete binds the target's current text the same way, so you can't overwrite something that was rewritten while you were reading it.

This is a review step, not a permission system. The code holds no secret, and a script can read it and rerun. Its job is to make the default path one where someone has looked at exactly what's going out. Accident, not malice, is what usually posts to the wrong channel at 3am. If something needs real authorization, this isn't it.

What we learned

Block the irreversible, warn about the merely unwise

Facts stop a send: a wrong code, a link Slack would break, an agent posting under a person's name. Judgement calls don't. A near-duplicate of a message already in the thread, a last message that's already yours, a mention nobody will receive and a send in the recipient's night hours each get one line of warning. Heuristics that can block teach people to reach for a bypass flag, and a bypass flag eventually gets used on the real gate. So send has no flag that skips confirmation.

An agent shouldn't speak as you by accident

One agent's slack ask went out under a person's name because it forgot --as-bot. Now a write from inside an agent is refused if it would post as a person, unless it names an identity: slack @deploy-bot send …, --as-bot or --as-user. Reads pass untouched.

A question is more than a message

Agents ask people things all the time, and free-text replies are hard to act on. slack ask posts the choices as reactions already on the message, so answering is one tap. But asking turned out to be the easy half. In one count, 13 of 71 questions had an answer nobody ever read back, because the asker had moved on. That's why questions gained a lifecycle: collect later with --waitFor, change with --edit, retire with --void, list what's stranded with --pending, and now --push, which hands the answer to the agent that asked.

A preview that can lie is worse than none

Anyone in a workspace can pick their own display name, and that name is drawn inside the preview you're deciding from. So terminal escape sequences and right-to-left overrides are stripped from it, and token-like strings are masked in previews. Files slack-term writes to disk go through secret redaction too.

Realtime can be a doorbell

Polling every channel is slow and burns rate limits, but mirroring a workspace's messages into a cloud service isn't something you want either. The relay, a Cloudflare Worker you deploy yourself, only rings. It passes on IDs (channel, timestamp, thread), not message text. The client then reads that one message with your own token. Polling still works, as a paced fallback that says so loudly.

Agents lose track of what they said

Every send, ask, poll and edit is logged locally with the process, directory, branch and session behind it. slack sent answers "which of my agents posted this?", and it's also what lets an answer find its way back to a living asker.

Work happens in more than one language

A URL glued to Chinese or Japanese text becomes a broken link, because Slack extends it into the sentence, so send refuses the ambiguous form and shows the fix. Japanese display names resolve as mentions, a question's wording follows its readers' language, and quiet-hour warnings use the recipient's timezone when Slack knows it.

Acknowledge without adding noise

Part of being a good participant is not posting. slack react is the cheap "seen" and "done", with no confirm step. pinlog keeps one pinned status message current and logs each change as a single thread reply, and tick checks off one item in a posted list.

A public repo with tests built from real traffic needs a guard

Our fixtures start as real Slack recordings, and real names have slipped through before. Now they're anonymized, including filenames, and one scanner checks each commit while another checks the whole tree before publishing. The second matters most, because data committed once never appears in a later diff.

Built for agents, usable by people

Output is plain text in a terminal and JSON when you ask. Errors and exit codes are meant to be branched on, and state lives in files, not a daemon. A typical loop looks like this:

# Wake on anything that mentions the bot, across channels and threads
$ slack stream --grep "<@U00000001>" --json

# Ask a person, as the bot, and move on
$ slack @deploy-bot ask "@bob" "Ship v2 today?" "Ship it" "Wait"

# Hand each answer to the agent that asked, as it arrives
$ slack @deploy-bot ask --pending --push --watch

# Say what's happening in the thread without notifying anyone
$ slack react "#eng:1700000000.000100" eyes

A .slack-term/ folder gives each repo or agent its own channel aliases, message prefix, inbox and outbox, found by walking up from where you run, like .git.

What it does

Read

slack news
Your mentions, grouped by day.
slack read "#eng"
Channel and DM history, with threads marked. --unreplied shows what still needs you.
slack thread
One whole thread.
slack search "deploy"
Full-text search across the workspace.
slack dump
Export channel history as markdown.
slack download
Save a file attachment.

Write, behind the confirm code

slack send
Post to a channel, DM or thread. A pasted permalink replies in that thread.
slack edit / delete
Change or remove a message you sent.
slack upload
Share one or more files.
slack schedule
Send later, list and cancel.

Coordinate

slack react
Acknowledge without growing the thread.
slack ask
A question with one-tap choices and an answer you can collect in a script.
slack poll
A reaction vote, counted for you.
slack todo
Task tracking on reactions, across a team.
slack pinlog
A pinned status board with a log in its thread.
slack lists
Read and update Slack Lists.

Listen and automate

slack tail "#eng"
New messages as they arrive, like tail -f.
slack stream
Every message matching a regex, across all channels and threads, with a resumable cursor.
slack relay init
Scaffold the realtime doorbell Worker.
slack inbox / outbox
Route messages to a directory as files, and queue replies the same way.
slack sent
Search what this machine posted, and which agent posted it.

Set up

slack auth
Sign in with a token or import a desktop or browser session. Several workspaces are fine.
slack @<who>
Act as a named bot or person.
slack doctor
Check a bot token can carry a two-way DM.

How it got here

From the git history. Many of these steps came from something going wrong or getting in the way.

  1. Mar 2026A Rust tool called sl: mentions and search. By the end of the month, sends need a confirmation.
  2. AprA TypeScript version joins and goes to npm, with multi-workspace profiles and a test suite built on anonymized recordings.
  3. MayEdit, upload, schedule and tail, plus handling for Slack's rate limits.
  4. JunThe first wait-for-a-reply primitive, tail --exit-on-message, and --as-bot, so a DM actually notifies someone.
  5. JulThe preview shows the thread you're replying to. Duplicate and double-post warnings, reactions, Japanese mentions.
  6. AugEvery gate names who you're acting as and binds that into the code. Quiet hours, todo, ask and poll.
  7. SepThe sent log records who posted what, and bots get session status for Slack's agent view.
  8. Octpinlog, the full question lifecycle, token masking in previews, stream and the relay.
  9. NovPer-directory scope with inbox and outbox, secret redaction, named identities with the refusal to post as a person, language packs, and answers pushed back to their askers.

Is it for you?

It suits scriptable conversations with a check before sending. The confirm step adds a second command, and you need a token with the right scopes. Other tools do other jobs better:
