# `ask` / `poll` / `todo` のマーカー絵文字 — 設計メモ

`todo` は `:pushpin:` を付けた**リアクション**でタスクを表現し、`has::pushpin:`
検索で一覧できる。同じことを `ask` と `poll` にもやりたい、という要望に対する
検討メモ。実装前にエッジケースを洗い出すのが目的。

結論だけ先に:

| コマンド | 未解決マーカー | 解決済みマーカー | 置き場所 |
|---|---|---|---|
| `todo` | `:pushpin:` 📌 | `:white_check_mark:` ✅ | リアクション |
| `ask` | `:question:` ❓ | `:white_check_mark:` ✅ | **本文先頭 + リアクション** |
| `poll` | `:ballot_box:` 🗳️ | `:bar_chart:` 📊 | **本文先頭 + リアクション** |

**決定事項 (taku 2026-08-24):**
1. `ask` は `:question:` を使い、**`todo` の needs-discussion からは ❓ を外す**
   (§1 の衝突を、`ask` 側を変えるのではなく `todo` 側を空けることで解消)。
   許容するリスクとして合意済み。
2. **日本語テキストに依存しない** (i18n)。パーサの識別子を日本語の指示文から
   マーカーへ移す。詳細は §6。
3. 型チェックは `tsgo` (`bun run typecheck`)。`tsc` は `typecheck:tsc` に残置。

以下、なぜこの形なのか。

---

## 1. 最大の落とし穴 — `:question:` は `todo` が既に使っている

`ask` に ❓ を、という要望はそのままだと**衝突する**。
`ts/todo.ts` の `DEFAULT_TODO_CONFIG.flags` はこうなっている:

```
needs-discussion  :question:
```

つまり ❓ は既に「要相談」フラグとして予約済み。`ask` のマーカーに同じ絵文字を
使うと、こうなる:

- `slack todo ls --state stuck` は「フラグが 1 つ以上付いた未完了タスク」を
  `(has::exclamation: OR has::question: OR …)` で引く。**`ask` の質問が全部
  "要相談タスク" として混ざる。**
- 逆に `ask` 側で ❓ を検索条件にすると、`todo` の要相談タスクが「未回答の質問」
  として出てくる。

`has:` は絵文字ごとの完全一致なので、**片方を変えない限り必ずぶつかる**。

**採用案**: `ask` は `:grey_question:` ❔ を使う。見た目は ❓ とほぼ同じで意図は
伝わり、`todo` の ❓ とは別の検索語になる。実測でもワークスペース内の
`has::grey_question:` は 0 件で、既存の使われ方を壊さない。

> 別案として「`todo` の needs-discussion を別の絵文字に変える」もあるが、
> こちらは**既に付いている既存メッセージが全部迷子になる**。リアクションは
> 過去に遡って付け替えられないので、意味を変えるより新しい語を取る方が安い。

`poll` は `:ballot_box:` 🗳️ (投票箱)。用途がそのままで、`todo` の
どのフラグとも重ならない。

## 2. リアクションではなく「本文の先頭」に置く

`todo` はリアクションでマークする。`ask`/`poll` で同じことをやると壊れる:

- **リアクションの枠を食う。** `ask`/`poll` は 1️⃣..🔟 を**種として自分で付ける**。
  そこにマーカーまで足すと、回答者が押すべきピルと、押してはいけない飾りが
  同じ列に並ぶ。押し間違いは「無効票」として集計に出るので、実害がある。
- **付け替えが投稿者にしかできない。** リアクションの追加/削除は誰でもできるが、
  「解決したら 📌 を ✅ に変える」のは投稿者の権限。一方 `ask`/`poll` は既に
  **本文を書き換えて**解決状態を表現している (`ASK_RESOLVED_PREFIX`)。
  マーカーも本文に置けば、状態が 1 か所にまとまる。
- **本文なら wire format の一部として検証できる。** 既に `askParseMessage` /
  `pollParseMessage` があり、往復テストで守られている。リアクションは
  そのテストの外側にあるので、ズレても気付けない。

現状すでに `ASK_RESOLVED_PREFIX = ":white_check_mark: "` が本文先頭にあるので、
**未解決側にも同じ位置にマーカーを置くだけ**で対称になる。

## 3. 検索 — `has::x:` はリアクション専用、本文の絵文字は引けない

2 つの検索経路があり、**混同すると静かに誤った結論に至る**。

### (a) リアクション → `has::pushpin:` (コロン込み!)

```
has::pushpin:      ← 正しい。リアクションのみにマッチ
has:pushpin        ← 誤り。エラーにならず全文検索へ退化する
```

`ts/todo.ts` の `hasTerm()` が生成しているのはコロン込みの形。
**コロンを落としても Slack はエラーを返さず、それらしい件数を返す。**
実際この設計メモは一度それで「リアクションは索引されない」という
誤結論に到達し、taku の指摘で訂正した (§6 の訂正節に詳細)。

実測 (2026-08-24、本番ワークスペース):

| クエリ | 件数 | 内訳 |
|---|---|---|
| `has::one:` | 15 | 抽出 8 件が **8 件ともリアクション有り、本文のみ 0 件** |
| `has:one` (誤形) | 2 | 本文に "One" を含む無関係な投稿 |

→ **`has::x:` はリアクション専用で、本文テキストにはマッチしない。**
→ **DM のリアクションも正しく索引される** (🗳️ を付けた DM の poll が
   `has::ballot_box_with_ballot:` で 1 件返る)。

### (b) 本文の絵文字ショートコード → 引けない

| クエリ | 件数 | 判定 |
|---|---|---|
| `":one:"` (引用符付き) | 50 | ✗ 無関係な投稿が並ぶ |
| `askv1` (英数字 1 語、投稿して実測) | **1** | ✓ 完全一致 |

`todo.ts` 冒頭の既存記録どおり、**全文検索は記号で分割する**。本文の
`:one:` は `one` として索引されるので、絵文字を本文に書いても検索語にならない。
記号を含まない英数字 1 語なら索引に載るが、機械語を本文に晒すのは読み手に
とってノイズなので採用しない。

**結論: 検索性はリアクション側 (`has::x:`) で担保する。** 本文のマーカーは
i18n のためのフォーマット識別子であって、検索のためではない。

## 4. その他のエッジケース

- **既存の投稿済み `ask`/`poll` はマーカーを持たない。** パーサは
  マーカーを**任意**として読む必要がある。必須にすると、いま飛んでいる質問が
  全部 `--waitFor` で回収不能になる (これは wire format の後方互換の話であり、
  `ts/ask.ts` 冒頭が繰り返し警告している事故そのもの)。
- **解決済みマーカーはパーサの分岐キーを兼ねている。** `askParseMessage` は
  先頭が `ASK_RESOLVED_PREFIX` かどうかで resolved / open を分ける。未解決側に
  マーカーを足すと、**先頭一致の判定が 2 つになる**。判定順を間違えると
  未解決を解決済みとして読む。open 判定は末尾の指示文で行い、resolved 判定を
  先に効かせる、という現在の順序を保つこと。
- **`poll` の解決済みは ✅ ではなく 📊。** 要望は「ask と poll の解決済みに
  checkmark」だが、`poll` の締切は「答えが 1 つに決まった」ではなく
  「集計が確定した」。✅ は `todo` の done と同じ語なので、締め切った投票が
  `todo ls --state done` 相当の検索に混ざる。📊 なら意味も検索語も分かれる。
  → **ここは要望と変えている。** ✅ に揃える方が良ければそう直す。
- **`:warning:` の無効票行と共存する。** 先頭マーカーと末尾指示文の間に
  無効票行が入る。行の walk-up ロジックは既にこれを飛ばすようになっているが、
  先頭にマーカーが増えると「質問文の開始行」がずれる。`askParseMessage` は
  `lines[0]!.startsWith("*")` を前提にしているので、**ここは必ず直す**。
- **マーカーは Slack が正規化する。** 投稿すると `text` は保存形が返る
  (既に判明済み: `1️⃣` → `:one:`)。マーカーも**ショートコードで書く**こと。
  グリフで書くと読み戻しで一致しなくなる。

## 6. i18n — 日本語をパーサから追い出す

現在の wire format は**末尾の日本語の指示文**でメッセージの種別を判定している
(`ASK_INSTRUCTION_REACTION_THREAD` など)。これは i18n と真正面から衝突する:
指示文を翻訳した瞬間、**過去の質問が全部読めなくなる**。文言がフォーマットの
バージョン識別子を兼ねている、という現在の設計そのものが多言語化を阻んでいる。

**方針: 識別子をマーカー絵文字に移す。**

```
:question: *質問文*            ← 先頭のマーカーが「これは ask だ」を意味する
...
_<指示文 — ここは翻訳してよい>_   ← もはや識別には使わない
```

マーカーは `:question:` というショートコードであり、**どの言語でも同一**。
これでフォーマット判定から自然言語が消え、指示文は自由に翻訳できる。

**後方互換**: 既に飛んでいる質問はマーカーを持たない。パーサは
「マーカーがあればそれで判定、無ければ**旧来の日本語指示文にフォールバック**」
の順で読む。旧フォーマットの読み取りコードは消さない。

### 検索は「英数字トークン」で行う (実測済み)

| クエリ | 件数 | 判定 |
|---|---|---|
| `":one:"` / `:one:` | 50 | ✗ コロンで分割され `one` 扱い |
| `askv1` (投稿して実測) | **1** | ✓ 完全一致 |

`todo.ts` 冒頭の既存記録と整合する。**記号を含まない英数字 1 語なら索引に載る。**
ただし本文に `askv1` のような機械語を晒すのは読み手にとってノイズなので、
検索性は**リアクション**側で担保する (下記)。

### ⚠️ 訂正の訂正: `has:` の構文はコロン込み `has::pushpin:` (2026-08-24)

一度「`has:` はリアクションを引けない / DM では索引されない」と書いたが、
**それは構文の誤りによる誤測定だった**。正しい構文はコロンで囲む形:

```
has::pushpin:      ← 正しい (ts/todo.ts の hasTerm() が生成しているのもこれ)
has::pushpin:        ← 誤り。ただの単語検索に落ちて本文にマッチする
```

`ts/todo.ts` の `hasTerm()` は最初からコロン込みで組み立てていた。
測定側だけが間違っていた。

| クエリ | 件数 | 内訳 |
|---|---|---|
| `has::question:` | 3 | 全て ❓ リアクション有り |
| `has::ballot_box_with_ballot:` | 1 | 🗳️ を付けた poll (DM) |
| `has::one:` | 15 | 抽出した 8 件は **8 件ともリアクション有り、本文のみは 0 件** |
| `has::one:` (誤形) | 2 | 本文に "One" を含む無関係な投稿 |

したがって:

1. **`has::x:` はリアクション専用**で、本文テキストにはマッチしない (実測 8/8)。
2. **DM のリアクションもきちんと索引される。** 🗳️ を付けた DM の poll が
   `has::ballot_box_with_ballot:` で正しく 1 件返る。
3. よって当初の設計どおり、**マーカーをリアクションとして付ければ
   `todo` と同じ検索体験が得られる**。

**マーカーの価値は 3 点に確定** — (a) i18n のための言語非依存な識別子、
(b) タイムライン上の視認性、(c) `has::question:` / `has::ballot_box_with_ballot:`
による横断検索。

> 教訓: `has:` 系を測るときは**必ずコロン込み**で書くこと。コロンを落とすと
> エラーにならず、静かに全文検索へ退化して**それらしい件数を返す**。
> 今回はそれで「リアクションは索引されない」という誤結論に一度到達した。

### リアクションとしても付ける → `has::question:` が使える

`todo` の `has::pushpin:` と同じ検索体験を得るため、マーカーは本文先頭に置くのに
加えて**リアクションとしても付ける**。§2 で「リアクションはピルの枠を食う」と
懸念したが、実際には `pollTally` はキーキャップ名のみを見て集計するので
無関係なリアクションは**既に無視される** (`tests/poll-format.test.ts` の
"unrelated reactions on the message are not votes" で検証済み)。よって実害はない。

これで:
- `has::question:` → 未回答/回答済みを問わず全ての ask
- `has::ballot_box:` → 全ての poll
- `has::white_check_mark:` → 解決済み (todo の done と共有)

## 5. 判断が要るところ

1. **`poll` の解決済みを ✅ にするか 📊 にするか** (§4)。
   要望は ✅ だが、`todo` の done と検索語が衝突する。現案は 📊。
2. **検索したいなら指示文アンカーを使う** (§3)。絵文字では引けない。
   `slack search '"下のリアクションで投票してください"'` が今すぐ動く。
3. 絵文字マーカー自体を入れるか。検索に効かない以上、価値は見た目だけ。
   入れる場合も**任意フィールド**として読むこと (§4 の後方互換)。
